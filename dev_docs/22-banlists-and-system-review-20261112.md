## 已修复问题

### P1：前导零卡号导致禁限标记丢失

`srvpro/cube-banlists.js` 以前用原始字符串做对象键。`03679218 0` 被保存为 `limits["03679218"]`，网页用数值卡号 `3679218` 读取时得到 undefined，于是显示无限制。原生 C++ 通过十进制 `strtoul` 读取，同一张卡在宿主仍会被禁止，因此出现构筑页和实际对战不一致。

线上只读证据：Duel current 为 `20261111-dg-filters-07419e9`，最新表为 `2026.10.01 OCG`，其中规范卡号键不存在、带零键的值为 0；该表共有 24 条带前导零的记录。最新 TCG 源文件同样有 24 条，不是单张卡的数据错误。

修复统一将键转换为 uint32 十进制数，并保留禁止值 0。加入前导零、重复覆盖、边界值、JSON 序列化和网页查表回归；发布健康检查现在逐条核对限制值，能拒绝“表名正确但所有卡都显示无限制”的版本。

### P1：迟到的比分轮询覆盖已生效的管理操作

`cube/apps/api/src/matches/matches.service.ts` 的 `doPollAll()` 在 `await roomStatus()` 前读取状态，响应后直接写回；原有建房路径的 generation 检查没有覆盖轮询。延迟响应测试复现了 webhook 已结算、冻结/回溯失效后仍写入，以及迟到 404 将已完成对局标为故障。管理员已录入结果的情况一并纳入回归保护。

修复在请求前及响应/404 后重新检查操作代次、当前阶段、冻结状态、房间名、结果和故障状态；为定时轮询增加防重入，避免多个慢查询周期重叠。6 项新增测试和完整比赛测试通过。未更改既有结果、重排比赛或操作线上数据库。

### P2：卡表索引及默认表选择不稳定

原解析器跳过非日期 `!Custom` 表头，而原生宿主保留它，后续所有索引可能错位。现在保留每一个表头及原加载顺序，不排序或去重；OCG/TCG/SC 有明确 format 与生效日期，自定义表保留原名称。构筑页默认只选已生效的最新 OCG，避免上游提前公布下期表后自动提前切换。

## 尚未修改的 review 发现

### P2：过期观战凭证会永久占用观战入口的容量

位置：`cube/apps/api/src/duel/duel.service.ts` 的 `standaloneWatch()`、`standaloneJoin()` 和 attach 定时器。

`standaloneWatch()` 每次创建新凭证，并用整个 `standalonePlayers.size` 判断 `maxConnections`，但不清理过期条目；清理只在玩家 join 路径执行。观战 socket 关闭也不删除对应记录。隔离复现将容量设为 2：创建两个未使用的观战凭证并将其过期，此时活跃 socket 为 0，第三次 watch 仍返回 `SESSION_LIMIT`。默认容量为 200。持续刷新观战页也会在一天内积累未过期条目。

建议分开统计活跃连接、短期未消费票据、可重连身份；至少在 watch/session/定时清理统一回收过期项，并为观众设置更短的闲置保留窗口。需明确断线重连语义后增加关闭、过期、API 重启恢复测试，避免简单删除凭证破坏重连。本轮作为独立后续修复项保留。

### P2：启动预热与实际服务各自导入一次完整卡库

位置：`cube/apps/api/src/main.ts` 的 `new CardsService().allCodes()`，以及 `cards/cards.service.ts` 的实例级 `loaded` / `ensureLoaded()`。

bootstrap 手工创建的实例不是 Nest 注入的实例。真实 CDB 模式故意不复用旧 SQLite 缓存，因此 Nest 实例首次收到请求会再次读取名称 JSON、主库/扩展库并重写卡片缓存。本地 15,161 条卡片的隔离实测：第一次导入 741 ms，新建第二实例再次导入 759 ms。这是同步工作，会落在首次业务请求路径上。

建议在创建 Nest 应用后通过 `app.get(CardsService)` 预热同一个实例；进一步以资源 manifest 指纹管理进程级只读卡片目录，避免启动逻辑依赖反复重建共享 SQLite 投影。

### P2：搜索分页前全量加载、筛选和排序阻塞事件循环

位置：`cube/apps/api/src/cards/cards.service.ts` 的 `searchPage()`（约 663 行起）。

当前先用 `LIKE '%token%'` 查所有匹配行，再在 JS 中做字段筛选、相关性/中文名称排序，最后才截取 24 张。查询计划显示全索引扫描，普通 B-tree 不能提供前缀定位。本地 Windows、15,161 条卡片、每种请求 25 次的实测如下；不是生产并发压测：

| 请求 | 匹配数 | 中位耗时 | P95 |
| --- | ---: | ---: | ---: |
| 空查询浏览、名称排序 | 14,896 | 65.36 ms | 67.74 ms |
| `龙`、相关性排序 | 2,272 | 22.12 ms | 25.68 ms |
| `a`、相关性排序 | 12,125 | 43.61 ms | 48.75 ms |

这些时间主要是同步数据库及 JS 运算，与轮抽定时器、HTTP、WebSocket 共用线程。建议先下推数值/类型筛选，缓存不变目录的排序索引和有限数量的查询结果；再评估适合中文子串语义的索引或 worker。不能直接把当前多字段子串搜索替换成默认 FTS 分词后宣称等价。

## 架构优化顺序

1. **统一异步结果提交检查**：轮询与建房已有相同的“发请求—等待—确认仍是同一代—写事件”需求，应抽成可复用的操作代次/状态检查，扩展到关闭房间、回溯和机器人生命周期。短期先解决观战凭证的生命周期。
2. **拆出只读卡片目录**：将卡库/名称/禁限表由不可变 manifest 绑定，搜索、卡组校验、API 元数据共用一次加载的目录；比赛事件与卡片索引分开维护。抓位统计目前每次校验缓存版本仍 JOIN 全部事件，长期可按 pool/tournament 保存显式投影版本，并使回溯时失效。
3. **部署规划与执行分离**：多份 Python/Bash 发布入口共用的状态机、包结构和组件哈希应集中定义，先生成可校验计划再执行。此次已把禁限表逐条验收和三个 JS 文件的完整性加入既有流程，后续应覆盖资源/App 混合版本的兼容检查。
4. **保持原生协议边界**：不因重写 srvpro 而同时更换协议、宿主参数和房间持久化模型。先用当前原生/网页互通夹具固定帧布局、重连、换备、消息隐藏和比分幂等行为，再逐模块替换。此次未改 ygopro/ocgcore 二进制协议。
