# 轮抽与小游戏发布评审

本轮从玩家报名、选牌、构筑、对战和小游戏房间逐一检查操作入口，并核对事件回放、管理员权限、独立 Duel 共用组件和 Aly 安装流程。集成基线为 `68b65a0`。

| 优先级 | 问题与影响 | 本轮改动及验收 |
|---|---|---|
| P1 | 开赛前退赛仍占确认名额，两名在赛玩家全部确认后比赛仍可能停在报名阶段 | 发牌事件持久化本场轮抽名单。确认人数、座位、传包和抓位统计使用同一名单。覆盖传堆和串行两种模式，以及开赛后退赛与恢复。旧事件按原名单回放。 |
| P1 | 提前进入构筑后返回选牌，传堆可能没有牌可选，串行可能缺少截止时间 | 返回时发出尚未发放的下一轮或恢复已有光标；重复恢复只发一次。轮抽完成后后台隐藏返回操作，直接调用接口返回冲突状态。 |
| P1 | 同一提交重新构建后复用发布编号，可能选中另一份候选包；安装中断也可能留下半成品 | 候选包绑定归档 SHA-256。每次检查文件、链接、build ID 和 SQLite 运行时，验证成功后才发布候选目录。完整安装锁定的 API 依赖，分别核对 Cube 与 Duel 静态文件。 |
| P2 | 卡组锁定、比赛冻结或进入对战后，构筑页仍展示拖拽、整理或快捷加入，用户操作才发现无法保存 | 在页面上按比赛状态控制编辑入口，继续支持查询卡片详情和下载 YDK。用浏览器覆盖锁定、冻结和比赛三个状态。 |
| P2 | 房主移除玩家、卡组修复和管理员轮询涉及多个页面，容易在二次确认、桌面与触屏切换时丢失上下文 | 验证猜卡、你画我猜经典及接龙的开始前房主管理、离房后的提示和重新加入；覆盖重复卡位置、键盘焦点、赛前修复确认及后台增量刷新。 |

## 放行顺序

1. 在隔离数据库验证 Windows、Linux 构建和回归，浏览器演练房主和玩家的完整流程。GitHub 的 Ubuntu、Windows 检查均通过后，以 merge commit 合入 `main`。
2. 从合并提交重建两份 Linux standalone 和 API，分别核对路由前缀、依赖及 build ID。在两份实例数据库的隔离副本上加载候选、核对完整性和业务记录。
3. 确认实例空闲条件及可恢复房间，备份数据库和配置后切换 API/Web。经 HTTPS 验证真实页面及其全部 JS/CSS、卡库、独立 Duel 配置和服务状态。
4. 两套应用各自验收后，将 annotated release tag 指向实际运行的源码，核对远端标签解引用结果。实例信息、房间标识与备份位置保存在私有回执。

## 下一轮观察

大型轮抽的事件回放和写事务会复制历史选牌及队列。下一次性能评估可按玩家人数、轮次采集延迟与堆内存，再决定是否缩减内存投影。改动前应使用旧快照和完整管理接口回归，保留历史回放及下载行为。
